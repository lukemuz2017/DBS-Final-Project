Runway · Draft for review

Data model

The tables behind Runway v1 and v2, how they link, and the decisions baked into them.

Postgres on Supabase · drafted Nov 13, 2026 · matches proposal v2

Decisions this model assumes

  • Supabase Auth, not Clerk. Auth comes with Supabase, and row-level security can check auth.uid() directly. Clerk would mean a second service, text user ids and extra token setup, for no gain on this project.
  • Two Supabase projects: dev and prod. Claude Code and its MCP server only ever touch dev. Prod holds testers' real bank data in v2.
  • Money is integer cents (bigint), and positive = money in. Providers' own sign conventions are normalized at the edge.
  • Every user table has user_id and row-level security. Deleting a profile deletes everything below it.
  • Forecasts are stored as runs, not only computed on the fly. That gives a fast dashboard and makes backtested accuracy possible.
  • Computed, not stored: two-week windows, positioning suggestions and estimated-tax amounts (unless overridden).

How the tables connect

Green = v1 (Nov 17) · amber = v2 (Dec 1) · red dashed = server-only · grey dashed = shared reference data. Transactions link many-to-one to the income stream or bill they match. The dashed “engine” arrow means the forecast engine reads the middle column (plus balances and transactions) and writes forecast runs.

How one dashboard number gets made

  1. Sync pulls accounts and transactions through the provider adapter, flips signs and marks internal transfers.
  2. Detection matches deposits to income_streams and charges to recurring_bills; the user confirms or edits them.
  3. The engine starts from today's balances in accounts marked include_in_forecast, adds each stream, bill, planned event and computed tax payment week by week, and builds a low, base and high case from each stream's spread and confidence.
  4. It writes one forecast_runs row and 12 forecast_weeks rows, with the reasons for any dip.
  5. The dashboard pairs weeks into six windows and flags any window whose low case drops below zero.

Security and row-level security

The standard policy, applied to every user table:

alter table accounts enable row level security;
create policy "own rows" on accounts
  for all using (auth.uid() = user_id) with check (auth.uid() = user_id);
  • Exceptions:
    • connection_secrets has RLS on and no policies, so only the server can read it.
    • forecast_runs and forecast_weeks are read-only for users; the engine writes them server-side.
    • tax_due_dates and the preset scenarios are readable by everyone.
  • A test proves it: sign in as user A and confirm that user B's rows return nothing.
  • Deleting an account first revokes the bank connection with the provider (Plaid /item/remove), then deletes the profile, which cascades to everything else.

Open questions for you

  1. Auth: OK to use Supabase Auth instead of Clerk? Choose Clerk only if the course requires it.
  2. Credit cards (decided Nov 17): card purchases are everyday spending; card payments from checking are internal transfers, never spending; what's owed on a paid-in-full card is one payment on its due date; a carried balance is debt paid down by a monthly bill. Card balances stay out of the cash total.
  3. Goals: should saved_cents be typed in by hand (simplest, v2) or tied to specific savings accounts (more accurate, more work)?
  4. Investments: included in the runway number, or only cash? I'd leave them out by default, since selling them takes time and they can drop.
  5. Tester data after Dec 1: delete all real bank data after the fair? I'd say yes, and add a “delete my data” button either way.
